# 输入卡顿排查与修复：一份可迁移的经验手册

> **适用**：桌面应用、编辑器插件、游戏 UI、嵌入式界面——凡是「用户实时输入」和「重量级 UI/业务工作」共用同一个串行执行器的场景。
>
> **来源**：2026-11 修 LTools「打开设置窗口时鼠标卡」的完整过程。案例的项目细节、线程模型与原始数据在 `docs/THREADING.md`；本文刻意抽掉框架细节，只留能搬到别的项目的方法。文中「本案例」是实例，括号里的 WPF / Win32 名词换成浏览器主线程、Qt 事件循环、Node 事件循环、游戏主循环、Android 主线程，方法一样。
>
> **一句话**：卡顿往往不是「干活太慢」，而是「实时输入和慢活排在同一条队列里」。先把输入延迟单独量出来，再把关键路径隔离到独立执行器，然后用同一把尺子证明「两者已脱钩」——这时就该停手。

---

## 1. 先把「卡」翻译成可测的量

用户说「卡」，至少是四种不同的东西，指标互不等价：

| 说法 | 真正该测的量 |
| --- | --- |
| 鼠标 / 键盘不跟手 | **输入事件从产生到被处理的排队延迟** |
| 画面掉帧 | 帧间隔 / 帧耗时分布 |
| 点了按钮半天才反应 | UI 事件到响应开始的延迟 |
| 整个程序像死机 | 主执行器被占用时长 / 看门狗超时 |

本案例用户说的是「打开设置时鼠标卡」，所以痛点指标是**输入延迟**，不是「设置窗口打开耗时」。但后者最容易被测到，也最容易被误当成原因。

> **动作**：分别定义「痛点指标」（对齐用户感受）与「嫌疑指标」（可能解释它），各埋一套点。只测最容易测的那个，会让你优化错东西还自以为有数据支撑。

---

## 2. 先量化，再动架构（设硬门槛）

线程 / 进程级改造的复杂度是不可逆的：一旦切开，跨线程状态、对象亲和性、关停顺序会长期跟着你。所以别凭「感觉是线程问题」就动手。

本案例把「阶段 0 = 只加探针、不改任何产品代码」设成硬门槛，写清楚：

- 什么数据出现才允许改线程模型：输入延迟尖峰与 UI 重活的时间窗口对齐，且最大值逼近系统强制踢掉的阈值（本案例 300ms 自动摘钩）；
- 什么数据出现就不许动：尖峰与 UI 重活无关，或延迟本身在噪声范围内。

数据出来是「开窗相位 p95 141ms、切页 max 297ms」，且构造期只有 23ms、说明大头在首帧渲染——门槛通过，才动架构。

> **动作**：把「继续 / 停止」的判据写成可执行的数值条件，写在改造方案里。事后再解释「我为什么改」都容易自圆其说。

---

## 3. 探针怎么设计才可信

这四条是本次踩出来的，通用性最强：

1. **用事件自带的时间戳**，不要用「处理时才打点」。队列里等了多久 = 事件产生时刻 − 进入处理时刻；事后补的日志测不到等待段。（本案例用输入事件结构里的 `time` 与进入回调时的系统 tick 求差。）
2. **归因要能穿越延迟**。事件被拖到某个相位结束后才处理，仍要归到造成延迟的那一段：按**事件自带时间**落在哪个相位窗口判定，别按处理时刻判定。否则最严重的样本会被记到「空闲」里，看起来一切正常。
3. **必须有「探针确实在工作」的计数器**。回调里累加一个事件计数——否则「延迟全 0」可能只是「钩子没装上 / 回调根本没跑」，这是最容易骗过自己的假绿。本案例 `hookEventsSeen=2224` 才让 0 延迟可信。
4. **别依赖不可靠的自定义标记**。本案例第一版用注入事件的 `dwExtraInfo` 做归因，结果整份数据空数组；直接作废、写明原因，不让它进对比表。探针默认关闭，只在诊断开关下启用，关闭时最多一次原子读。

> **动作**：设计探针时先问「这份 0 是真好还是假好」，再问「归因错一位会怎样」。数据允许作废，但必须留下作废记录。

---

## 4. 找根因：谁和谁排在同一条队列

抽象模式：**实时性敏感的路径与重量级工作共用同一个串行执行器**。

本案例的机制是「输入回调由安装它的那条线程的消息泵派发」，而同一条线程还跑窗口渲染、切页、控件构造——一条队列里两种工作，重活一占住，输入只能排队。

可复用的检查表：

- 输入回调由谁派发？和 UI 渲染 / 布局 / 大列表构建是不是同一个 loop？
- 这个 loop 上有哪些**同步**重活：首帧渲染、布局重算、大数据序列化、磁盘 IO、同步网络、脚本编译？
- 有没有外部看门狗会在超过阈值时把你踢掉（摘钩、ANR、断连）？本案例的 300ms 不是「体验差」，是**功能直接失效**。
- 尖峰是否与重活的时间窗口对齐？这是因果，不只是相关。

> **动作**：画出「执行器 → 上面跑的所有工作」清单。根因通常不是某个函数慢，而是这份清单里混进了两类延迟要求完全不同的工作。

## 5. 分阶段改，每阶段用同一把尺子复测

| 阶段 | 做什么 | 成本 | 何时进入下一阶段 |
| --- | --- | --- | --- |
| 0 · 量化 | 只加探针与场景驱动，不改产品逻辑 | 低 | 数据确认痛点与嫌疑对齐 |
| 1 · 同执行器减负 | 惰性创建、只刷当前页、对象复用、预热、后台落盘 | 低、不引入线程边界 | 痛点指标仍不达标 |
| 2 · 隔离关键路径 | 把**输入链路**搬到独立执行器 | 中，需要跨线程改造 | 复测后按第 6 节判断 |
| 3 · 继续拆分 | 把 UI 也拆到另一线程 / 进程 | 高 | **需触发器命中**，默认不做 |

阶段 1 必须优先：本案例惰性建页 + 只刷当前页就把开窗从 206ms 降到 94ms（-55%），一行线程代码都没改。阶段 2 才在「切页 max 仍 281ms 逼近阈值」时动手。

> **动作**：阶段之间只换「被改的东西」，不换探针、不换归因、不换场景。换了尺子，前后数据就不可比，等于白测。

## 6. 读懂「两条曲线脱钩」——什么时候该停

本案例决定性的数据是这一组：

| | 阶段 0 | 阶段 1 | 阶段 2 |
| --- | --- | --- | --- |
| 输入延迟（开窗相位 p95 / 切页 max） | 141ms / 297ms | 78ms / 281ms | **0 / 0** |
| UI 开窗耗时 p50 | 206ms | 94ms | 91ms |

阶段 2 之后 **UI 耗时几乎没变（甚至偶尔更高），输入延迟却归零**。这说明两者已经解耦：UI 该慢还是慢，但不再顶住输入。

> **通用判据**：如果痛点指标已归零、而嫌疑指标没变，说明两者已脱钩，**继续优化嫌疑指标对痛点零收益**。这是「停手」信号，不是「还差一步」信号。

两个常见自欺：

- 把「架构看起来更彻底」当目标——再拆一层 UI 线程很解气，但收益命题是空的；
- 把两个议题混成一个——「设置窗口自己开得慢」是 UI 性能优化，和「输入被 UI 顶住」不是同一个问题，别借前者的名义动线程模型。

## 7. 隔离关键路径前，先把代价认下来

切开执行器必然带来这些，做之前逐条确认有出口：

- **不能同步等待对方**。一 `Invoke` / `Join` / 等结果，延迟又绑回对方忙不忙上。只单向投递、只排队不等待。
- **副作用要有唯一出口**（本案例 `Ui.Post`）。散落的跨线程调用迟早在某些低频路径上炸，而且很难复现。
- **共享状态要重新归属**：谁独占、谁只读、谁需要锁 / 原子可见性。列一张「状态 → 所有者 → 同步方式」表再写代码。
- **带线程亲和性的对象不能碰**：窗口、菜单、弹层、UI 控件通常只认创建它的线程。回调里改用不可变只读快照（发布时整份替换，不在原对象上改字段）。
- **定时器可能依赖原执行器**：本案例的长按计时器从 UI 定时器换成通用定时器，因为新线程没有 UI 消息泵。
- **卸载 / 关停必须在拥有它的那条执行器上做**，且不要在调用线程上等它结束（否则退出流程会永久卡死）。
- **最容易被漏的一条**：所有会改变「只读快照」的入口都要补一次发布。漏一个，表现是「偶发、难复现、看起来像时序玄学」——本案例补了窗口开关、激活、钉住态、菜单开合、子菜单展开、拖动合并等十几个推送点。

> **动作**：把这份代价清单当成改造的验收项，而不是「出 bug 再补」。跨线程 bug 的特点正是低频 + 难复现。

## 8. 参考实现怎么查，以及证据边界要诚实

想知道成熟产品怎么做，别只信一种来源。本案例用了三方交叉：

- **静态边界**：竞品的 P/Invoke 程序集里有消息泵 API、钩子三件套、线程消息唤醒 API；
- **自身日志**：日志里有一条被显式命名为 `HookDispatcher` 的线程，而设置窗口与切页的 100% 日志都落在主线程槽位；
- **自己的量化**：输入延迟与 UI 耗时脱钩，说明「隔离输入」这条路足够。

结论是：**参考实现隔离的是输入，不是 UI**；它靠页对象复用（`Reused=True` 9 条 avg 8ms vs `Reused=False` 133 条 avg 32.2ms）和启动预热在同一个 UI 线程里减负——正好对应本案例的阶段 1 + 阶段 2。

但必须写清证据等级：日志线程槽位是**观测到的分布**，不是 API 级的「窗口句柄 ↔ 线程 ID」归属；目标进程当时未运行，主程序集体积过大只能做部分分析，前端语义分析超时。所以准确表述是「**没有证据显示做了，且日志强烈指向没做**」，不是「已证明没做」。

> **通用教训**：把「没找到证据」写成「找到了没做的证据」，是技术复盘里最常见的自欺。结论要标强度，边界要写在结论旁边，别藏在脚注里。

## 9. 给未来的自己留一个触发器

「暂不做」不等于「永远不做」，但重新评估的条件必须可度量、且能排除假象。本案例写在设计文档里的触发器：

- 同一探针复测，痛点指标 p99 > 100ms 或 max ≥ 300ms，**且事件计数正常**（排除探针没工作）；
- 关键路径上新增了挪不走的同步重活（单次 > 50ms），把新执行器自己的泵顶住；
- 真机复现且探针能复现尖峰；
- 需求方明确提出物理隔离（不是因为输入卡顿）。

同时写清「真要做之前先补哪些地基」，以及「触发后先重跑阶段 1 那类减负，别直接跳到最重的方案」。

> **动作**：触发器的每一条都要能被自动复测判定。「感觉又卡了」不是触发器。

## 10. 回归：自动化只能覆盖一半

自动化能查：构建 0 警 0 错、探针三相位、日志无异常、无崩溃记录、静态检查。

**必须真人走一遍**的是被跨线程改造动过的交互路径，按四类列：

- **状态平衡**：吞掉按下必须同时吞掉抬起；锁存状态只能由「抬起」清；达到上限自动收尾。
- **焦点与层级**：模态窗的 Owner、弹层置顶顺序、点击不把后续注入的输入打到自己身上。
- **坐标与缩放**：多显示器、不同 DPI 下的定位与命中判定。
- **关停**：退出不卡死、卸载在正确的执行器上完成、没有残留线程 / 窗口。

这类路径自动化极难伪造真实输入，别拿「构建过了」当验收。

## 11. 一页速查

```text
[ ] 1. 把「卡」翻译成一个可测的痛点指标，并另设嫌疑指标
[ ] 2. 加探针：事件自带时间戳 / 归因穿越延迟 / 事件计数 / 默认关闭
[ ] 3. 用一份基线数据决定「要不要动架构」，写死继续与停止的判据
[ ] 4. 画出执行器上的全部工作，确认实时输入与重活是否同队列
[ ] 5. 阶段 1：同执行器减负（惰性 / 复用 / 预热 / 后台）
[ ] 6. 同尺复测；不达标才进阶段 2
[ ] 7. 阶段 2：隔离关键路径，逐条对齐第 7 节代价清单
[ ] 8. 同尺复测；看「痛点归零 + 嫌疑没变」是否已脱钩 → 是则停手
[ ] 9. 参考实现三方交叉验证，结论标注证据强度与边界
[ ] 10. 写下可度量的重新评估触发器
[ ] 11. 真人回归四类路径：状态平衡 / 焦点层级 / 坐标缩放 / 关停
[ ] 12. 归档：有效数据、作废数据及原因、决策理由
```

## 12. 反模式速查

| 反模式 | 为什么错 | 该怎么做 |
| --- | --- | --- |
| 只看平均耗时 | 卡顿是尾延迟问题，p50 常常一直是 0 | 看 p95 / p99 / max，以及是否逼近硬阈值 |
| 把相关性当因果 | 「开窗慢 + 输入卡」不代表前者导致后者 | 相位归因 + 隔离后的脱钩验证 |
| 探针没有存活计数 | 「0 延迟」可能只是探针没跑 | 回调里累加事件计数，随结果一起导出 |
| 凭直觉直接拆线程 | 代价不可逆，且可能根本不是队列问题 | 先量化设门槛，先做同执行器减负 |
| 每阶段换一套测法 | 前后不可比，改完说不清有没有效 | 同一探针、同一归因、同一场景 |
| 症状消失后继续拆架构 | 收益命题已空，只剩复杂度 | 把「痛点归零 + 嫌疑没变」当停手信号 |
| 在回调里同步等 UI | 延迟重新绑回 UI 忙不忙 | 单向投递、只排队不等待 |
| 快照只在主要入口发布 | 漏一个就是偶发难复现的错判 | 列出所有状态变更入口，逐一补发布 |
| 把「没找到证据」写成「证明没做」 | 结论强度虚高，后续决策被误导 | 标明观测层级与未覆盖的范围 |
| 用构建通过代替真机验收 | 跨线程问题低频且难自动复现 | 按四类路径真人点一遍 |
